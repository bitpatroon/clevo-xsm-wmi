                        API MONITOR CAPTURE ANALYSIS
                    Clevo X370SNx Keyboard Color Change
═══════════════════════════════════════════════════════════════════════════════

FINDINGS:

1. TOTAL API CALLS CAPTURED: 37,659
   - Most are standard Windows API calls (malloc, file I/O, registry, etc.)
   - Only relevant ones: DeviceIoControl via KERNELBAS.dll
   
2. INSYDE DCHU.dll ACTIVITY:
   ✓ InsydeDCHU.dll is loaded during monitoring
   ✓ This is the interface to ACPI/EC communication
   
3. COLOR DATA PATTERNS FOUND:
   - Red (FF 00 00):   20,598 occurrences
   - Green (00 FF 00): 17,189 occurrences  
   - Blue (00 00 FF):  147,876 occurrences
   - White (FF FF FF): 77,794 occurrences
   
   ⚠️ These are mostly FALSE POSITIVES from:
     - String data structures
     - UI color definitions
     - Memory padding
   
   NOT from actual EC commands!

4. WHY NO ACTUAL HARDWARE COMMANDS VISIBLE:
   
   The RGB bytes we see are in KBLED.dll's data structures and UI definitions,
   NOT in the actual DeviceIoControl buffers sent to AcpiBridge.
   
   This is because:
   - CC40.exe calls KBLED.dll functions
   - KBLED.dll has the RGB values embedded
   - But the actual EC commands are sent via:
     * Windows WMI (via InsydeDCHU.dll internally)
     * Direct ACPI method calls (not visible in this user-mode capture)
     * Or kernel-mode driver communication (below API Monitor's tracing level)
   
5. MISSING PIECE:
   
   We're capturing user-mode API calls, but the actual WMI/ACPI communication
   might be happening inside kernel-mode drivers (AcpiBridge.sys) where 
   API Monitor can't easily trace.

NEXT APPROACH - BREAK THROUGH THE WALL:

Instead of API Monitor sniffing (which isn't giving us what we need),
we should:

1. Use a KERNEL DEBUGGER (WinDbg) to break into AcpiBridge.sys when it's
   called by KBLED.dll
   
2. OR: Extract the actual function signatures from KBLED.dll and use
   Ghidra/IDA to reverse-engineer what it sends
   
3. OR: Since we already have KBLED.dll decompiled strings showing:
   - SetRGBLeftColor(R, G, B)
   - SetRGBMidColor(R, G, B)
   - SetRGBRightColor(R, G, B)
   - SetWMI() / SetWMIPackage()
   
   We can ASSUME these call WMI MethodId 0x68 (MethodId for RGB)
   with buffer format: [R, G, B, brightness/zone_selector]

RECOMMENDATION:

Given what we know from the DSDT:
- MethodId 0x68 = Full RGB color (confirmed in DSDT SCMD handler)
- Arguments = 32-bit ARGS with packed RGB bytes
- EC sends: [0x03, 0x00, 0xC1, byte1, byte2, byte3, byte4, 0x00]

And from KBLED.dll strings:
- SetRGBLeftColor(R, G, B) function exists
- SetRGBMidColor, SetRGBRightColor, etc. exist
- These likely map to MethodIds 0x67-0x6D

BEST PATH FORWARD:
→ Build a Linux driver that calls ACPI MethodId 0x68 with RGB values
→ Test by writing a simple /dev/keyboard-led control interface
→ Mirror the KBLED.dll API (SetRGBLeftColor, etc.)
